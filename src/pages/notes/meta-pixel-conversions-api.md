有一種帳戶，出價調過、受眾換過、素材也重做了，成效就是拉不起來。回頭去看事件管理工具，發現 Purchase 事件一天只收到個位數，實際成交明明不只這些。

系統看不到轉換，就沒有東西可以學。它只能照著點擊和曝光去找人，找回來的人再怎麼便宜也不是會買的那群。追蹤沒接好的時候，後面所有調整都在瞎猜。

## 先決定要收哪幾個事件

埋點的第一個常見錯誤是埋太多。把 Meta 列出的標準事件全部埋一遍，每個頁面都放一個，最後拿到一堆稀疏的資料，哪一個都不夠系統學。

實際上一條漏斗留三到四個就夠。內容瀏覽、加入購物車、開始結帳、完成購買，這樣一條線可以覆蓋大部分的最佳化需求。名單型的業務更簡單，內容瀏覽加上完成註冊或送出表單就能跑。

挑事件的標準是它會不會被拿來當最佳化目標，以及一週內能不能累積到足夠的次數。一週跑不到幾十次的事件，設成最佳化目標只會讓廣告組一直卡在學習階段。

參數要跟著事件走。購買類的事件帶上 `value` 和 `currency`，之後才算得出廣告投資報酬率。商品型的帶 `content_ids` 和 `content_type`，動態廣告和目錄要靠這兩個欄位對上商品。

## 瀏覽器端會掉多少

Pixel 是一段跑在瀏覽器裡的 JavaScript。它能不能把事件送出去，取決於使用者那一端的環境。

廣告封鎖外掛會直接攔掉請求。Safari 的智慧防追蹤會限制第三方 Cookie 和指令碼寫入的存留期。iOS 上使用者若沒同意追蹤，可用的識別資訊也跟著少。實務上看到的落差從一成到超過三成都有，流量來源越偏行動裝置和 Safari，掉得越兇。

掉的不只是數量。轉換少報，系統會低估這組廣告的價值，出價跟著保守，投遞量再往下掉，數字看起來就更差。

## Conversions API 從伺服器端補

Conversions API 走的是另一條路。轉換發生在你自己的伺服器上時，由伺服器直接把事件送到 Meta，不經過使用者的瀏覽器，也就不受外掛和瀏覽器設定影響。

一筆事件大致長這樣。

```json
{
  "event_name": "Purchase",
  "event_time": 1756272000,
  "event_id": "order_20260827_10231",
  "action_source": "website",
  "event_source_url": "https://example.com/checkout/done",
  "user_data": {
    "em": ["<sha256 of email>"],
    "ph": ["<sha256 of phone>"],
    "client_ip_address": "203.0.113.10",
    "client_user_agent": "Mozilla/5.0 ...",
    "fbp": "fb.1.1756271000.1234567890",
    "fbc": "fb.1.1756271000.IwAR..."
  },
  "custom_data": { "value": 1280, "currency": "TWD" }
}
```

`em` 和 `ph` 這類個人資料要先做 SHA-256 雜湊再送，送之前記得統一格式，電子郵件轉小寫去掉前後空白，電話號碼去掉符號並補上國碼。原始值直接送出去會被退。

## 兩邊都送，靠 event_id 去重

Pixel 和 CAPI 同時開著，同一筆購買會送兩次。這是設計上就預期的做法，兩條路互為備援，哪一條通就算哪一條。

去重靠 `event_id`。瀏覽器端和伺服器端針對同一次轉換產生同一組 `event_id`，`event_name` 也一致，Meta 會自動判定為同一筆，保留先到的那一個。

`event_id` 通常直接用訂單編號，或在後端產生一組唯一值同時寫進頁面。兩邊各自亂數產生就一定對不起來，會真的算成兩次。

設定完先去事件管理工具看去重狀態，那裡會顯示有多少事件被判定成重複。數字對了再開跑，不要設定完直接下預算。

## fbp、fbc 和比對品質

CAPI 送出去的事件能不能對到真實的人，看 `user_data` 裡帶了什麼。這件事有一個分數，事件比對品質，範圍 0 到 10。

六以上還能用，八以上算好。想拉高就多帶幾個參數。電子郵件的雜湊值通常貢獻最大，電話、姓名、外部識別碼、IP 位址和 User Agent 都算。

`fbp` 和 `fbc` 這兩個值特別容易被漏掉。它們是 Pixel 寫在瀏覽器裡的 Cookie，`fbc` 記著使用者是從哪一次點擊進來的。這兩個值存在瀏覽器端，要在使用者提交表單或下單的時候一起送到後端，再由後端放進 CAPI 的請求裡。少了它們，點擊和轉換之間的關聯就斷了，歸因會變差。

## 網域驗證和八個事件的限制

要投轉換型廣告，網域驗證躲不掉。三種方式挑一種做完就好，在 DNS 加一筆 TXT 紀錄、上傳一個 HTML 檔案到根目錄、或在網頁的 `<head>` 裡放一個 meta 標籤。

驗證通過之後，才能替這個網域設定事件的優先順序。這裡有個硬限制，每個網域最多八個事件，而且要排出先後。同一個使用者觸發了多個事件時，只有排最前面的那一個會被回報。

排序的原則是把價值最高、最靠近成交的放在最上面。購買排第一，開始結帳第二，加入購物車第三，依此往下。排錯的後果是實際成交被排在後面的事件蓋掉，回報看起來就少了一截。

改動優先順序會有一段冷卻時間，改完不要馬上又改。

## 上線前跑一遍

設定完成之後，按這個順序驗一次。

1. 事件管理工具的測試事件分頁，帶上 `test_event_code` 送幾筆，確認瀏覽器端和伺服器端都收得到。
2. 看診斷分頁有沒有警告，缺參數、格式錯誤、重複率異常都會列在這裡。
3. 實際下一筆測試訂單，確認 `value` 和 `currency` 的數字對得上。
4. 隔天回頭看事件比對品質分數穩定在幾分。

這四步做完，投放才有意義。跳過驗證直接下預算，錢會花在一組看不見成效的廣告上，而且要過好幾天才發現。

## 我們這邊怎麼做

一佳的代投服務包含 Pixel 埋點與廣告成效追蹤的設定。Pixel 建立在我們的 BM 底下，跟著資產那一層走，換廣告帳戶的時候接得過去，歷史事件不會歸零。
